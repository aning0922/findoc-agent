# 系统架构

FinDoc Agent 由 React 工作台和 FastAPI 服务组成。系统将原文问答、财务分析和经营研究分为不同流程，共享文档来源与证据读取能力。财务金额由已确认事实和确定性计算提供，模型用于证据选择与解释草稿。

## 三条执行流程

| 流程 | 输入与处理 | 输出 |
| --- | --- | --- |
| 原文问答 | 在选定报告中检索，模型选择证据编号；服务端恢复对应原文，校验来源版本和引用。 | 原文摘录、页码、引用和独立保存的问答记录。 |
| 经营研究 | 选择单企业两期或双企业同期模板，核对已保存事实，执行财务计算，检索经营原文，再生成解释草稿。 | 财务变化、经营原文、待审解释和已保存的研究任务结果。 |
| 报告管理 | 读取已完成的经营研究，复验事实与来源，组织草稿；用户保存或追加版本。 | 可读回的报告版本及指定版本的 Markdown。 |

当前报告生成入口使用已完成的经营研究任务。单次原文问答记录不直接作为报告生成输入。原文问答遇到增长率、差额等计算请求时，会要求转到财务分析流程。

## Agent 与 LangGraph 的职责

[原生工具循环](../app/agent/tool_loop.py)处理模型的工具调用请求，包括工具白名单、JSON 参数、schema、来源范围、重复调用和步数限制。只有通过校验的请求才会交给业务服务执行，服务端工作空间与文档范围由应用注入。

[经营研究工作流](../app/agent/operating_research_graph.py)使用 LangGraph 管理阶段、持久化检查点和人工等待。[研究模板](../app/research/templates.py)负责固定业务顺序：检查资料和事实、等待必要的人工操作、计算三项财务变化、检索经营原文、校验解释并保存结果。模型输出继续经过受控循环和引用校验；研究范围和执行顺序由模板约束。

人工介入分为三个动作：

1. **接受候选**：用户对照原文，确认金额、单位、期间与口径，系统保存接受记录。
2. **保存财务事实**：将接受的整组数据存入事实库，后续分析通过事实 ID 和来源版本读取。
3. **继续研究**：用户返回等待中的任务并明确继续，工作流重新检查来源与事实后执行。

任务累计记录步骤、工具、检索和模型调用预算。页面刷新和历史 GET 只读取已保存状态；运行中的任务遭遇进程中断后会记录中断状态，不自动重复模型调用。

## 文档、证据与财务计算

文档处理保留正文、表格、物理页和可用的布局坐标。来源版本关联文档 ID、文件 SHA-256、处理尝试与解析器版本。检索、原文读取、财务事实和报告引用均需匹配这些身份。

[多文档问答](../app/rag/selected_evidence.py)采用原文摘录方式：模型只返回选中的证据编号，服务端填入原文和表格上下文，避免模型改写年份、数字或单位。引用校验确认出处与所选资料一致；原文是否足以支持研究判断仍需人工核对。

财务抽取支持营业收入、归母净利润、经营活动现金流量净额。系统保留原始金额和单位，将接受后的数值规范为人民币元，并通过 [Decimal 分析服务](../app/agent/financial_analysis.py)计算差额、同比或同期相对差异。缺期、口径冲突、零基数与负基数分别处理，不能计算的情况有明确结果状态。

PDF.js 根据对应来源版本展示原页。只有持久坐标与实际 PDF 文字通过校验时才显示高亮；缺少坐标时保留原页和文本。

## 报告与存储

报告生成复用已保存的经营研究，分别保留财务结果、原文、模型解释和用户编辑。追加版本不会覆盖旧版；读取和导出也不会重新执行研究、调用模型或计算金额。导出前会重新检查来源、接受记录和研究结果是否仍有效。

| 存储 | 内容 |
| --- | --- |
| `documents.db` | 文档、企业、来源、财务事实、研究任务及报告版本等业务记录。 |
| `agent-runs.db` | 兼容单文档 Agent 的运行和事件记录。 |
| `objects/` | 上传的原始文件。 |
| `milvus.db` | 本地向量索引。 |

上述文件位于 `FINDOC_RUNTIME_ROOT` 指定的目录。数据库与文件存储共同支持来源检查，但不构成跨存储事务；后续读取仍需重新验证来源。
