## G2：F31 的开始请求阻塞完成，运行中矩阵与取消在现有 UI 不可达

**要求：** 02/07 明确“异步受限任务”“读取正在运行结果”“取消未执行的任务”。

**源码证据：** `batch_research/api.py` 的 POST `/batches` await `service.start`；
`service.py` 在串行 cell 循环和最终提交之后才返回。数据库较早已保存 batch ID，
但正常 POST 响应尚未返回。`BatchResearchPanel.tsx` 在 `await fetch` 期间置 busy；
仅 consume 响应或手工 recovery 才设置 matrix；查询原操作按钮 `disabled={busy}`；
取消按钮依赖 matrix 且 `disabled={busy || !!pending}`。因此当前约 120 秒工具执行
完成证明不能代替运行中矩阵/取消可用性。即使仅加后端 ack，若 receipt 仍 UNKNOWN
且 pending 未分离，现有 `locked` 仍会锁住取消，应同步修交互状态。

**独立复证（临时 SQLite + 实际 ASGI 路由，工具为 fake）：** 第一格通过 Event 暂停，
POST task 未完成；并行 GET 原 operation 已可取 batch ID；矩阵是
`dispatching, queued, queued, queued`；通过测试客户端主动取消可取消 3 格；释放第一格
后 POST 才返回 200，最终 `completed,cancelled,cancelled,cancelled`，只执行 1 格。
所以不是“后端没有取消”，而是常规浏览器无法在需要时取得/操作该能力。

**最小修复/验收：** 持久化原 operation、batch ID、child UUID 后及时 ack，由受限
worker 继续原计划，UI 立即轮询矩阵并允许独立取消 queued 项。保持 UNKNOWN 不重放、
进程重启不自动续发模型。至少一个真实浏览器批次在首格运行时显示后续 queued，
点击取消后未开始项不 dispatch，已完成项可读。主控审计中已开始修改 batch WIP；
本结论针对 e510876，WIP 不自动视为关闭。
